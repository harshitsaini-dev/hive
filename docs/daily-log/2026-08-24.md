# 24 August 2026

## Blocked images looked like broken ones

Reported from a phone: opening a newsletter showed a grid of grey
broken-image icons. Working as designed, and still a bug.

The CSP does block remote images, deliberately — loading one tells the sender
the message was opened, and that is the tracking pixel this app refuses to
fire. What it did not do was remove the *claim* that a picture was there. The
markup still said `<img src="https://…">`, the browser tried, failed, and drew
the broken-image icon. To a reader that is indistinguishable from Hive being
unable to render the message.

Now the `src` is moved aside into `data-blocked` before the frame is written,
so the browser never has an image to fail at, and a line above the message
says how many were held back and why — with a **Show images** button that
re-renders with them allowed.

Not a setting and not remembered, on purpose: consenting to load a sender's
images is consenting to tell them you opened the message, and that is a
decision about one message rather than a preference about all of them.

Two regex characters were eaten by a Python escape on the way into the file
again — `\b` became a backspace and `\2` a control character. Third time this
session. Worth remembering that a "just patch it in" script is a lossy channel
for anything containing backslashes.

## The zoomed-out phone, found

Reported twice, and I could not reproduce it — which was the useful part,
because the arithmetic could. In the screenshot the header band ended at
573/640 of the screen: 89.5%, which is exactly what a 360px-wide element looks
like when the browser has scaled a **402px-wide document** down to fit a 360px
viewport. So the page really was too wide, and my probes were too clean to
show it: three tidy stub messages, none of them hostile.

Feeding an unbreakable 120-character token through each field one at a time
found it in seconds. A long **sender name** took the document from 360px to
**1203px** — and a phone browser responds to that by zooming the entire
application out, from one row that may well be scrolled off-screen.

Three distinct causes, sharing only the symptom:

1. **A flex item will not shrink below its content.** The sender name had no
   `min-width: 0`, so the row was as wide as the name. Same for the subject
   and snippet, which had ellipses but nothing to shrink into.
2. **A column with `align-items: flex-start` is sized by its own children.**
   The accounts list sized each line to its content and the column to the
   widest line, so nothing downstream had a narrow box to wrap into. Stretched
   instead.
3. **`overflow-wrap: break-word` does not reduce min-content width.** It wraps
   identically to `anywhere` and differs in the one way that mattered: a flex
   item's automatic minimum *is* its min-content, so the row stayed as wide as
   the address however the shrink factors were set. `anywhere` lets it
   collapse.

`overflow-wrap: break-word` is now on `body` as a general guard — untrusted
strings are everywhere in a mail client — with `anywhere` where a flex
minimum needs breaking.

There is a permanent test now: the same token through every field of every
view, asserting `document.scrollWidth <= window.innerWidth` on the message
list, the reading pane, the analysis panel, accounts, rules and the drawer. It
measures rather than inspects, because the three causes had nothing in common
except the number they produced.
