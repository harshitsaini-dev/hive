# 24 August 2026

## Blocked images looked like broken ones

Reported from a phone: opening a newsletter showed a grid of grey
broken-image icons. Working as designed, and still a bug.

The CSP does block remote images, deliberately — loading one tells the sender
the message was opened, and that is the tracking pixel this app refuses to
fire. What it did not do was remove the *claim* that a picture was there. The
markup still said `<img src="https://…">`, the browser tried, failed, and drew
the broken-image icon. To a reader that is indistinguishable from Hive being
unable to render the message.

Now the `src` is moved aside into `data-blocked` before the frame is written,
so the browser never has an image to fail at, and a line above the message
says how many were held back and why — with a **Show images** button that
re-renders with them allowed.

Not a setting and not remembered, on purpose: consenting to load a sender's
images is consenting to tell them you opened the message, and that is a
decision about one message rather than a preference about all of them.

Two regex characters were eaten by a Python escape on the way into the file
again — `\b` became a backspace and `\2` a control character. Third time this
session. Worth remembering that a "just patch it in" script is a lossy channel
for anything containing backslashes.

## The zoomed-out phone, found

Reported twice, and I could not reproduce it — which was the useful part,
because the arithmetic could. In the screenshot the header band ended at
573/640 of the screen: 89.5%, which is exactly what a 360px-wide element looks
like when the browser has scaled a **402px-wide document** down to fit a 360px
viewport. So the page really was too wide, and my probes were too clean to
show it: three tidy stub messages, none of them hostile.

Feeding an unbreakable 120-character token through each field one at a time
found it in seconds. A long **sender name** took the document from 360px to
**1203px** — and a phone browser responds to that by zooming the entire
application out, from one row that may well be scrolled off-screen.

Three distinct causes, sharing only the symptom:

1. **A flex item will not shrink below its content.** The sender name had no
   `min-width: 0`, so the row was as wide as the name. Same for the subject
   and snippet, which had ellipses but nothing to shrink into.
2. **A column with `align-items: flex-start` is sized by its own children.**
   The accounts list sized each line to its content and the column to the
   widest line, so nothing downstream had a narrow box to wrap into. Stretched
   instead.
3. **`overflow-wrap: break-word` does not reduce min-content width.** It wraps
   identically to `anywhere` and differs in the one way that mattered: a flex
   item's automatic minimum *is* its min-content, so the row stayed as wide as
   the address however the shrink factors were set. `anywhere` lets it
   collapse.

`overflow-wrap: break-word` is now on `body` as a general guard — untrusted
strings are everywhere in a mail client — with `anywhere` where a flex
minimum needs breaking.

There is a permanent test now: the same token through every field of every
view, asserting `document.scrollWidth <= window.innerWidth` on the message
list, the reading pane, the analysis panel, accounts, rules and the drawer. It
measures rather than inspects, because the three causes had nothing in common
except the number they produced.

## Drafts, Spam, folder-scoped analysis, and selection that works like a list

Six things, and one bug found along the way that mattered more than any of
them.

**Drafts and Spam are destinations.** Each is its own Gmail folder, and a
search inside them stays inside them — unlike the inbox, where searching
reaches archived mail, here the folder *is* the question.

**A search from any of them cannot escape**, and "all mail" now excludes
drafts as well as spam and trash: an unsent draft is an answer to a different
question than "where is that email".

**The bug.** The bulk-action bar branched on `mode === 'inbox'` to decide
between "Move to Trash" and "Restore / Delete forever". Harmless while Inbox
and Trash were the only two lists — and the moment Sent, Drafts and Spam
existed it offered *permanent deletion* in all three. ADR 0002 puts that
behind one typed confirmation in one place. It branches on Trash now, and a
test walks all five folders asserting the button appears in exactly one.

**The analysis follows the list beside it.** It always measured the whole
mailbox, which put "10,605 messages match" next to an inbox reading 8,361 —
both correct, answering different questions, with nothing on screen to say so.
It now measures the folder on screen, says which, and offers "Whole mailbox"
for the old behaviour.

**A sender search** narrows the results already in hand. Two hundred rows is a
lot to read, and filtering them is typing rather than another few minutes of
quota for an answer the last run already contains.

**Clearing shows progress.** It resolves a query and trashes in batches, one
account at a time — seconds for a handful, over a minute for thousands, all of
it behind a button that said "Clearing…" and nothing else. The honest reading
from the other side of the screen was that the app had hung. The unit is a
step rather than a message, because the message count is not known until each
resolve returns and a bar measured in them would finish before the work did.

**Pages are a hundred, not five hundred.** Five hundred was right when every
page came from Gmail and fewer round trips mattered. Searches are answered
from the index now and come back with a real total, so a page is a window
rather than the answer — and a hundred rows renders and scrolls far better.

**Selection**: shift-click for a run, drag across the boxes, Ctrl/Cmd+A for
the page and again to clear it. Ctrl+A is ignored in a text field, where the
browser's own meaning is obviously the one intended.

That last one took four wrong turns worth writing down, because each was a
different lie:

1. A **stale closure** — a drag fires a handler per row, faster than React
   re-renders, so reading `selected` directly meant every step built on the
   value from the render it was created in. Everything goes through the setter
   now.
2. **`preventDefault` on a checkbox click** reverts the browser's own toggle,
   and React — seeing the same `checked` prop as last render — has no reason
   to touch the DOM. The row then showed the opposite of what the app
   believed, which is how every range came out exactly one short. The box is
   `readOnly` and driven from `mousedown`, so the DOM never joins the
   argument.
3. **A `dragging` flag** set on mousedown and cleared on mouseup kept
   extending after the button was released: moving the pointer toward the next
   thing to click crosses rows, and those were being painted as part of a
   drag. `event.buttons` cannot go stale.
4. **`mouseenter` is missable by design** — a fast drag jumps whole rows
   between frames and never enters them. The drag reads what is under the
   pointer instead, and takes a range from the anchor rather than accumulating
   crossings.

And two of the "failures" were the test lying rather than the app: ticking the
first row makes the bulk bar appear and pushes the list down, so coordinates
measured beforehand pointed a row too high; and the pointer cannot be moved
past the bottom of the window, so at 720px the third row was simply
unreachable.

## Spam was empty because Gmail was never asked for it

Reported an hour after Spam shipped: Hive said "Nothing in Spam" beside a
Gmail tab listing nine messages.

`users.messages.list` excludes SPAM and TRASH unless `includeSpamTrash` is
set, and it is a **gate in front of the results rather than a filter on
them** — `q=in:spam` without the flag returns nothing at all. An empty folder
and a folder Gmail declined to show look exactly the same from here, which is
why it read as a mismatch rather than an error.

Hive never sent the flag. Three consequences, only one of them reported:

1. **The Spam view was always empty**, whichever way it was answered.
2. **The Trash view was quietly wrong too.** Served from the index it showed
   only messages trashed *through Hive* — the write-through sets the label
   locally — and never anything trashed in Gmail itself. That is the view
   permanent deletion lives in.
3. **The index has never contained Spam or Trash**, despite a comment in
   `sync.ts` claiming it covered "the whole mailbox, trash and all".

Fixed by deriving the flag from the query rather than passing it around:
`needsSpamTrash()` looks for `in:spam`, `in:trash` or `in:anywhere`, so no
caller can build a query for one of those folders and forget the switch that
makes it work. The backfill sets it outright, because the index is meant to be
everything.

Existing indexes are still missing both folders and there is no way to tell
from the rows — an account with no spam and an account whose spam was never
fetched are identical. So `sync_state.covers_spam_trash` records whether the
backfill that built an index asked for them, and until it is set those two
folders are answered from Gmail directly. Deliberately not forcing a
re-index: rebuilding is hours of quota per account to recover two folders that
read perfectly well without it.

## Four reports, four different lies

**The Sent analysis said 163 beside a sender list adding to thousands.** Same
failure as yesterday's inbox mismatch, in a worse place — inside one panel.
The totals come from Gmail and honoured the folder; the rollup came from the
index and ignored the query entirely, counting the whole mailbox. It took a
bare account id, so there was nothing for it to honour. It takes the same
query as the page listing now, and the run carries its scope structurally as
well as as a Gmail string — built alongside each other rather than parsed from
one to the other, because guessing at Google's grammar to recover structure is
how the two halves drift apart again.

Drafts, Spam and Trash all get the same treatment, and an analysis of Spam or
Trash falls back to Gmail when the index predates the fix that put them in it.

**"Indexing auto nahi hoti."** It did — hourly, which on a multi-thousand
message backfill is indistinguishable from stopped, and which meant a pass
lost to a rate limit cost a full hour before anything tried again. That is
what turned "Index now" from a nudge into a habit. The sweep runs **every ten
minutes** now (an incremental pass is one history call, so repeating it costs
almost nothing) and the card says when the next check is due — and, when the
last one was rate-limited, that it will try again then. Work that happens on
its own has to say so.

**"Indexing — 26,829 of about 501."** `messages.list` returns a
`resultSizeEstimate` which is not an estimate of anything useful: on a mailbox
of tens of thousands it came back as the page size plus one. The real total
comes from the profile's `messagesTotal` now, and any figure below what is
already indexed is not shown at all — one obviously wrong number destroys
confidence in the two beside it.

**Reloading always returned to the inbox.** Only `/accounts` was addressable;
every other destination lived in React state, so a refresh felt like being
sent home and a link to a folder could not exist. Every view has a path now,
Back walks through where you have been, and one test that had encoded the old
behaviour was corrected rather than kept.

Also: **Ctrl+A has three states** rather than two — this page, everything the
search matches, then nothing. Pressing it twice used to clear the selection,
which is a strange thing to ask for twice; the second press obviously means
"no, all of it".

Drag-selection was left exactly as it was, on request.
