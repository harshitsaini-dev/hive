
## Selection, counts and the reach of search

Reported: a mailbox holding 1,323 messages showed 1,264 in Hive. Not data
loss — the view had loaded two full pages plus a partial third, and the
"Select all 1,264 loaded" label presented that running total as if it were the
mailbox. A count that is really a floor must not be shown as a headline.

Changed:

- **Two explicit controls instead of one.** "Select page (N shown)" ticks what
  is on screen; "Select all matching" resolves the query server-side and
  selects every match. Both are present from the start — the second used to
  appear only once the page was fully ticked, which made them read as one
  escalating control.
- **The bulk bar says which is which** — "N selected on this page" versus
  "N selected — everything matching this search".
- **The blast-radius cap went from 5,000 to 10,000.** Real mailboxes are that
  size and stopping halfway made people run the same cleanup twice. The wall
  still exists and the UI still says when a search exceeded it.
- **Ctrl+K hand-off no longer narrows.** The palette lists results from every
  folder of every account, then handed the text to an `in:inbox` view, which
  silently dropped most of them. That search now opens as "Search results"
  with no folder scope. Choosing a section in the sidebar leaves it.
- **The palette footer says its list is the top 25**, not the whole match.

Also fixed: the root `typecheck` script ran bare `tsc --build` against a
`tsconfig.json` that does not exist, so it had never done anything. It now
fans out across the workspaces, which is what CI was already doing.

86 Playwright tests, green headed.

### Searching from a folder was hiding the mailbox

Follow-up to the above, reported against the deployed app: a search for a word
plus "has attachment" returned nothing while the mail plainly existed. It had
been archived, and archived mail is not `in:inbox` — so the folder the user
happened to be standing in was quietly excluding most of their own mailbox
from their own search.

Browsing a folder is still the folder. But the moment any filter is applied
the folder scope drops and the search covers everything except spam, the way
Gmail's own search does. The header says which it is ("Search results —
searching all mail: inbox, sent, archived and trash") and offers a one-click
"Only search Inbox" to narrow back, with "Search everywhere" to widen again
without retyping. The Trash view keeps its scope, because there the bin is the
subject.

The empty state now says which reach came up empty, rather than a flat
"Nothing matched those filters."

89 Playwright tests, green headed.

### The rest of the results now load themselves

Reported: "filter sirf usi page par lagta hai" — the filter looked like it only
applied to the page on screen. It never did; the query goes to Gmail and covers
the whole mailbox. But the results came back 500 at a time behind a "Load 500
more" button, so a search that had matched 1,323 messages presented as a search
that had matched 500, and one that matched 12 old messages could present as
nothing at all.

The view now pages the rest in on its own, up to the 10,000 bulk cap, showing
"Loading the rest — 1,000 of 1,323" with a **Stop here** to interrupt and
**Keep loading** to resume. When it finishes it says "All N matches loaded",
so a list that ends reads as complete rather than truncated.

The total comes from `resolve-query`, which pages message ids 500 at a time and
costs nothing next to the metadata behind them — so the real number is on
screen long before the messages it counts are.

89 Playwright tests, green headed.
