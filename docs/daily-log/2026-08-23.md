
## Selection, counts and the reach of search

Reported: a mailbox holding 1,323 messages showed 1,264 in Hive. Not data
loss — the view had loaded two full pages plus a partial third, and the
"Select all 1,264 loaded" label presented that running total as if it were the
mailbox. A count that is really a floor must not be shown as a headline.

Changed:

- **Two explicit controls instead of one.** "Select page (N shown)" ticks what
  is on screen; "Select all matching" resolves the query server-side and
  selects every match. Both are present from the start — the second used to
  appear only once the page was fully ticked, which made them read as one
  escalating control.
- **The bulk bar says which is which** — "N selected on this page" versus
  "N selected — everything matching this search".
- **The blast-radius cap went from 5,000 to 10,000.** Real mailboxes are that
  size and stopping halfway made people run the same cleanup twice. The wall
  still exists and the UI still says when a search exceeded it.
- **Ctrl+K hand-off no longer narrows.** The palette lists results from every
  folder of every account, then handed the text to an `in:inbox` view, which
  silently dropped most of them. That search now opens as "Search results"
  with no folder scope. Choosing a section in the sidebar leaves it.
- **The palette footer says its list is the top 25**, not the whole match.

Also fixed: the root `typecheck` script ran bare `tsc --build` against a
`tsconfig.json` that does not exist, so it had never done anything. It now
fans out across the workspaces, which is what CI was already doing.

### Searching from a folder was hiding the mailbox

Follow-up to the above, reported against the deployed app: a search for a word

### Auto-loading was the wrong answer, and Gmail said so

The automatic paging added earlier the same day is reverted. It hit Gmail's
per-minute quota almost immediately and the API started refusing:

    403 PERMISSION_DENIED — Quota exceeded for quota metric 'Queries' and
    limit 'Queries per minute per user' (15,000)

The arithmetic was never going to work. Every message on a page costs a
metadata read, so one 500-message page across three mailboxes is already about
half the minute's allowance — and the loop was set to fetch up to ten thousand.

What ships instead:

- **Pagination stays manual.** The page shows 500 and a "Load 500 more"
  button. What was actually wrong was never the paging; it was that a page
  looked like the whole answer.
- **So the page now states the whole answer**: "Showing 500 of 1,323 matches",
  resolved from message ids, which page 500 at a time and cost almost nothing
  next to the metadata behind them.
- **Rate limits are retried, not shown.** Gmail signals a per-minute breach as
  a 429 *or* as a 403 whose body says `rateLimitExceeded` — the second reads
  like a permission failure and was being surfaced as one. Both now back off
  and retry up to four times.
- **Google's error envelope no longer reaches the screen.** A rate-limited
  search put six hundred characters of nested JSON in front of the user,
  project number included. It says one sentence now.
- **Appended pages are deduplicated.** A cursor that fails to advance replays
  its last page, and a list holding the same messages twice looks exactly like
  a filter that stopped being applied partway down. Nothing new in a page also
  ends the paging rather than offering another lap.

Also added: a **custom date range** (`after:` / `before:`) beside the age
presets. "Older than a year" cannot express "that job I had in 2019", and the
raw-syntax box is not an answer for someone who came here to avoid the syntax.
Gmail's `before:` is exclusive, so the end date is pushed out by a day to make
an inclusive-looking range inclusive.

### A custom calendar, real scrollbars, and pictures that show up

Three things that all came down to the same thing: the browser's own widget
does not know it is inside this app.

**Date picker.** `<input type="date">` styles its box and nothing else — the
calendar is drawn by the browser, so a pale panel dropped out of a dark app,
and a different pale panel on the next machine. `DatePicker.tsx` replaces it,
with the same bar the custom dropdown had to clear: arrows walk the grid a day
at a time, PageUp/PageDown change month, Home/End reach the ends of the week,
Enter commits, Escape closes, and the grid carries the roles a screen reader
expects. Month and year are dropdowns rather than chevrons, because reaching
2019 from 2026 by clicking eighty-four times is not a date picker. Values stay
`YYYY-MM-DD`, so nothing downstream knows it changed.

Dates are held at UTC midnight throughout. A calendar day is not an instant,
and `new Date(y, m, d)` read back as an ISO string lands on the day before in
any negative-offset timezone — which is how pickers end up off by one.

**Scrollbars.** There was no scrollbar styling at all, so every scrolling
surface drew the OS default: a grey trough with stepper arrows against a dark
rounded panel. Now themed, on `*` rather than `body` — the sidebar, the
message list and the reading pane each scroll in their own box, and a rule on
the page would have left all three untouched.

**Attachment images.** A photo showed as a filename and a broken-image icon.
Two causes behind one symptom:

- Attachments were only ever served `application/octet-stream` with a download
  disposition, so no `<img>` could ever render one. There is now an
  `?inline=1` mode — but the server decides, by **sniffing the magic bytes**,
  not by trusting a parameter or the sender's `Content-Type`. Raster formats
  only. SVG is an image and is deliberately excluded: it is a document that
  can carry script, and rendering one in this origin would run it with the
  session's cookies.
- A body that embeds its picture writes `src="cid:…"`, pointing at a
  `Content-ID` on an attachment part. The parser now keeps that id and the
  reader rewrites those references to the attachment endpoint, which is
  same-origin and allowed by the frame's CSP.

Remote `http(s)` images are still blocked and deliberately not rewritten:
loading one tells the sender the message was opened, and that is the tracking
pixel this app refuses to fire. There is a test asserting the request is never
made.

### Mailbox analysis

The empty half of the mail view now holds a dashboard: how much mail matches,
how much of it carries a file, who sent it, and a way to clear a sender out.

**The two halves are priced completely differently, and the UI says so.**
How many messages match and how many carry an attachment come from lists of
message ids — 500 an API call, so a hundred thousand of them is a couple of
hundred cheap calls and the numbers are *exact*. Working out who sent them
needs the `From` header of every single message, one metadata read each,
against a quota of about three thousand a minute. A hundred thousand messages
is therefore roughly half an hour of fetching for the sender list alone.

So the run reads the newest slice at a depth the user picks — 2,000 up to
Everything — reports exactly how deep it got, and says plainly when the list
is not the whole mailbox. The totals beside it always are. A sender list that
quietly described a fraction while looking like it described all of it would
be worse than no sender list.

Found while building it: reusing `MAX_BULK` for the id listing capped the
*counts* at ten thousand, so a hundred-thousand-message mailbox would have
reported a total of ten thousand — a wrong number presented as a fact.
`MAX_BULK` limits the blast radius of an action; nothing is destroyed by
counting, so the analysis uses its own, far higher ceiling.

Each sender row offers **View** and **Clear**:

- *View* fills the list beside the panel with that sender's mail. Clearing 812
  messages on the strength of a number alone is a leap — an address you
  half-recognise could be receipts — and the answer has to be reachable
  without losing an analysis that took minutes.
- *Clear* always **trashes**, never deletes. A chart is a place to notice
  something, not a place to destroy mail from; permanent deletion stays behind
  the typed confirmation in the Trash view, per ADR 0002. There is a test
  asserting `delete-forever` is never called from here.

A finished run is kept in `localStorage`, so a reload does not throw away
minutes of work and a slice of the quota. Only counts and sender addresses —
the same metadata already on screen, on the reader's own device, never a
message body. If the filters change after a restore, the numbers are marked as
belonging to the old ones and **Clear is withheld** until it is re-run: it
builds its query from the controls, so acting on stale figures would trash a
different set of mail than the number on screen. View stays enabled, because
looking is reading.

### The analysis becomes a real feature

Everything below is one thread: making the analysis panel worth the minutes it
costs to produce.

**Stored in the database, not the browser.** localStorage met "do not throw it
away on refresh" and none of "see it from anywhere". `analysis_runs` holds one
row per user — counts and sender addresses only, the same metadata the mailbox
list already shows, never message content. /privacy says so now.

**Runs outlive the page.** The job was always detached from the request; what
was missing was a way back to it. The server tracks the in-flight job per user
and `/analytics/last` reports it, so closing the tab a minute into a scan and
coming back reattaches instead of paying for the work twice.

**Scheduled runs**, in the Rules view beside the cleanup rules. Daily or
weekly, at an hour of the user's choosing, so the answer is waiting rather
than being watched. It carries **no action** — a schedule produces numbers;
clearing mail still needs a person to press the button and confirm. There is a
test asserting the card contains no mention of deleting or trashing, which is
what should stop a future change from quietly adding one.

The schedule time is stored as **minutes past midnight UTC**, not an hour.
03:00 in India is 21:30 UTC; rounding that to hour 21 and converting it back
gives 02:00, so the schedule walked backwards an hour every time the page was
opened. A few hundred million people live in a half-hour offset — not an edge
case worth rounding away.

**The totals are the filter.** All / with attachments / without are pressable
and narrow everything below them. So are per-mailbox chips. Both are free: the
run already recorded each sender's total, attachment count, and split by
account, so switching views is arithmetic rather than another scan. What is
pressed scopes the actions too — a figure of 12 that belongs to one mailbox
must never clear 812 across three.

**Multi-select on senders**, because junk arrives in clumps and eleven
newsletters cleared one confirmation at a time is eleven chances to misclick.
Selected senders view as one `from:(a OR b)` query but clear one request at a
time, so a partial failure leaves a known state.

**A re-run keeps the old numbers on screen** until the new ones land. Blanking
the panel made "Run again" feel like it had destroyed the answer, and during
the minutes a scan takes the old figures are still the best ones there are.

### The browser's own dialogs are gone

`window.confirm` titled itself with the domain name, in the OS colours, in the
middle of a themed app — and blocks the page thread while it is up. Replaced
by `ConfirmDialog` for the reversible actions (clear a sender, delete a rule,
disconnect an account). `ConfirmDestructive` still guards permanent deletion
with its typed phrase; an OK button is proportionate only when the answer to a
misclick is "restore it from Trash".

### "Gmail could not complete this search" was a lie

The new analysis tables existed locally and not in Turso — migrations only ran
when someone remembered to run them from a laptop. Fair enough. What was not
fair enough is what the app said about it: **every** failure in a mailbox
route was reported as "Gmail could not complete this search", so a missing
table sent the investigation off towards the Gmail API for a problem entirely
on this side.

Three fixes, in order of how much they matter:

1. **The error no longer blames Gmail for our faults.** A database failure
   says so, in as many words, and the original error is logged either way.
2. **The server applies migrations at boot.** Logged and continued rather than
   fatal — refusing to start over a transient database hiccup would take the
   service down, and every route already fails on its own terms.
3. **A failed save no longer discards a finished run.** Storing the result is
   a cache write; throwing there would have thrown away minutes of Gmail quota
   and reported a storage fault as an analysis failure.

Also fixed while in there: the migration CLI compared `process.argv[1]` to
`import.meta.url` as plain strings, which never matches on Windows — a
backslashed path against a `file://` URL.

### The sync engine

`message_index` has existed and been empty since day one. It is filling now,
and the analysis reads from it.

**The case for it stopped being theoretical.** One asymmetry in the Gmail API
drives nearly everything in this project: counting matches is cheap (ids come
back 500 to a call) and learning *anything about* a message is not (a metadata
request each, against roughly 3,000 a minute). So the sender rollup — the one
question the analysis panel exists to answer — costs about half an hour on a
hundred-thousand-message mailbox, every single time it is asked. From a local
index it is a `GROUP BY`.

**Two phases, deliberately separate** (`apps/server/src/sync.ts`):

- *Backfill* walks the mailbox a page at a time, recording Gmail's own page
  token as it goes, and stops after ~2,000 messages per pass. Built to be
  interrupted — restart, rate limit, a free instance spinning down — and to
  resume rather than start again. The per-pass cap is not a limit on mailbox
  size; it is a limit on how long one account can hold the quota, so a
  multi-hour backfill cannot starve the interactive app.
- *Incremental* applies `history.list` from a stored cursor, and only once the
  backfill is complete. Applying history to a half-filled index would leave
  holes nothing would ever go back and fill.

The cursor is taken **after** the backfill, not before: taken first, anything
arriving during an hour-long backfill would fall between the two phases and
never be indexed. Gmail's ~30-day history window expiring is handled as an
instruction rather than an error — drop the index and rebuild.

**Attachments needed a second pass.** Gmail's metadata format omits the MIME
parts entirely, so there is no way to tell from what the backfill already
fetched. The `has:attachment` search knows, and asking it costs an id list —
no metadata reads at all. That answer is stored in a new column so the
analysis never asks again.

**An indexed mailbox is no longer sampled**, so its sender list stops being
"the newest N of M" and starts being the whole thing — the truncation warning
disappears on its own once the backfill finishes.

The hourly sweep does one pass per account per tick rather than finishing one
mailbox before starting the next, which would leave every other account cold
for hours. Accounts shows real progress — "Indexing — 12,500 of about
103,412" — and says why when it stalls, because silence looks identical to
"nothing has changed". There is an **Index now** button for anyone who does
not want to wait for the next tick.

Still metadata only: sender, subject, snippet, labels, date, and now a
has-attachment flag. /privacy updated to match.

### Scheduled analysis becomes scheduled indexing

The scheduled-analysis feature is gone, migration and all. It made sense while
every run meant a Gmail request per message and therefore minutes of waiting;
the index removed the reason. A run against an indexed mailbox finishes
immediately, so there is nothing left worth scheduling — what wants keeping
current is the index, and the hourly sweep already does that.

Its slot in the Rules view is now an **Indexing** card: per-mailbox progress
with a bar, "Index now", and pause/resume. Pausing is a real choice — someone
who connected a mailbox only to send from it should not pay for a background
index supporting a search they will never run. The table was dropped rather
than left unused, because a settings table nobody writes to is a trap for
whoever next reads the schema.

Accounts keeps the status line and loses the controls: that page is for
connecting and disconnecting, and the index is background work.

### Two real bugs the deploy surfaced

**`Indexing stopped: Gmail profile request failed (403)`** on a mailbox whose
tokens were fine. Two faults compounding:

1. `getProfile` used a raw fetch with no backoff, and Gmail reports an
   exhausted per-minute quota as a **403** whose body says `rateLimitExceeded`
   — which reads like a permission problem. It is called immediately after a
   backfill has just spent a minute's quota, so it was close to guaranteed.
2. Worse: that call was part of the same step that marks the backfill
   complete. The final page leaves no page token, so a failure there meant the
   next pass found neither a token nor a completion flag and **started the
   whole mailbox again** — hours of work and quota discarded by a request that
   had nothing to do with the index.

The completion flag is now written first and the cursor fetched separately; a
backfill that finished but has no cursor takes one on the next pass instead of
rebuilding. And `getProfile` backs off like everything else.

### Labels that had stopped being true

The scan-depth options said "about a minute", "very slow", "can take hours".
Honest when written, wrong the moment a mailbox finishes indexing — and wrong
for exactly the people most likely to read them. A stale scary label is worse
than none, so the estimates are gone.

### Search reads the index

The other half of the index's payoff. A page of 500 from Gmail is 500 metadata
reads; from the index it is one query, and it comes back with a real total
rather than "however many happen to be loaded".

**The bar for using it is that the answer must be identical**, which is what
most of the design is about:

- **Free text always goes to Gmail.** Gmail searches message bodies and the
  index holds sender, subject and a snippet, because storing bodies is exactly
  what the privacy policy forbids. A text search that quietly stopped matching
  words inside messages would be a worse product wearing a faster one's
  clothes. Raw Gmail syntax goes to Gmail for the same reason — the index
  cannot promise to interpret it the way Google does.
- **Structural filters are answered locally**: folder, sender, date range,
  age, category, attachments, unread. The client sends these *alongside* `q`,
  never instead of it, so the server picks and falls back without the client
  knowing which happened.
- **Falling back is always allowed and never silent-in-the-wrong-direction.**
  Not backfilled, indexing paused, catch-up failed — any doubt at all returns
  null and the search goes to Gmail. Slower is a cost; wrong is not.
- **The index is freshened before it is read.** The sweep runs hourly, which
  is fine for an analysis and not fine for an inbox — a message from four
  minutes ago has to be there. One `history.list` call closes the gap, and it
  is skipped entirely if the last catch-up was under a minute ago.

Paging has two shapes now: Gmail hands back a cursor per mailbox, the index
counts rows and takes an offset. The list handles both, and the count line
prefers the index's exact total over the estimate it used to have to resolve
separately.

### Body search, made fast without storing bodies

Asked for: "indexing should make body search fast too." The obvious reading —
index the message text — is the one thing this project has promised not to do.
`message_index` is metadata only and /privacy depends on it.

It turns out not to be necessary. A search has two halves and only one of them
was ever expensive:

- **Finding the matches** is a `messages.list` with a query. Ids come back 500
  to a call, and Google does the matching — inside the bodies, exactly as
  before.
- **Turning those ids into rows** was the cost: one metadata request per
  message, so 500 requests for a page of 500.

The second half the index can do for free. A text search now asks Gmail for
ids and hydrates them locally, so a search of a fully indexed mailbox costs
**one Gmail call regardless of how many messages it matches**. Anything not
yet indexed — mail from seconds ago, a mailbox still backfilling — is fetched
normally, and Gmail's ordering is preserved either way.

So body search stays exactly as capable as it was, and stops being slow. The
index still holds no message content, and nothing about the privacy policy
changes.

### Two bugs the index introduced, found before anyone hit them

Reading searches from the index made two omissions load-bearing that had been
harmless while everything went to Gmail.

**`history.list` ignored label changes.** It parsed `messagesAdded` and
`messagesDeleted` and nothing else. But trashing a message does not delete it
— it swaps `INBOX` for `TRASH`, which arrives as `labelsAdded`/`labelsRemoved`
and nothing else. So mail thrown away in Gmail's own UI stayed in Hive's inbox
until a full re-index. Changed messages are now re-read rather than having
their label set reconstructed from a stream of additions and removals, which
is the kind of cleverness that is wrong once and then wrong forever.

**Hive's own actions did not reach the index.** Trash five hundred messages,
let the list refresh, and all five hundred were still there — the action had
succeeded at Gmail, and the list now reads from an index that had not heard
about it. Indistinguishable, from the user's side, from the trash button not
working. Bulk actions now write through to the index immediately; the next
history pass overwrites those rows with Gmail's own version anyway, so the
local correction is temporary by construction. It is wrapped in a try/catch
that logs rather than throws: the mail has already moved, and failing the
action over its bookkeeping would report a success as a failure.

Also removed `idsFromIndex`, which I wrote during the search work and never
wired up. Dead code in a repository layer is a trap for whoever assumes it is
used.

### Sent mail showed the address instead of the name

Reported: mail sent through Hive arrived as `harshitsaini.dev` where the
sender's name should have been.

`getSendAsDisplayName` was preferring the account's **default** alias over the
alias for the address actually being sent from. Wrong in both directions:
sending from a second connected mailbox borrowed the default account's name,
and — the case that showed up — when the default alias carried no display name
at all, the function returned null and Gmail fell back to the local part of
the address.

The alias for the sending address now wins; the default is only a fallback.

No unit-test runner exists in this project (Playwright at the API boundary is
the whole suite), and the Gmail call this depends on is server-to-Google, so
the selection rules were exercised directly instead: exact alias with a name
beside a nameless default, a non-default second alias, an address with no
alias at all, and an alias whose name is blank.

### The sender name, properly this time

The alias-ordering fix was correct and not sufficient: mail still arrived as
`harshitsaini.dev`, and from all three accounts. So the `sendAs` lookup is
either failing or genuinely returning nothing, and the code could not say
which — it caught every error and returned null, which is indistinguishable
from "this alias has no name". Both end with a bare address on screen and
nothing anywhere explaining why.

Two changes:

- **The lookup logs what happened.** Status and body on a failed request, and
  a line when the call succeeded but carried no name. Guessing at a black box
  is not debugging.
- **The name can be set in Hive.** `connected_accounts.display_name`, editable
  from Accounts, used ahead of whatever Gmail reports. Null keeps the current
  behaviour, which is the default and usually right — this exists because
  "usually" is not "always", and there is nothing to infer harder about: the
  person knows what they want to be called.

Accounts now states what recipients will actually see rather than leaving it
to be discovered by sending something.

The stored name is stripped of CR and LF before it is saved. It ends up in a
`From:` header, and a newline in one is header injection — the same guard
`buildRawMessage` already applies, applied earlier so nothing unusable is ever
stored.
