
## Selection, counts and the reach of search

Reported: a mailbox holding 1,323 messages showed 1,264 in Hive. Not data
loss — the view had loaded two full pages plus a partial third, and the
"Select all 1,264 loaded" label presented that running total as if it were the
mailbox. A count that is really a floor must not be shown as a headline.

Changed:

- **Two explicit controls instead of one.** "Select page (N shown)" ticks what
  is on screen; "Select all matching" resolves the query server-side and
  selects every match. Both are present from the start — the second used to
  appear only once the page was fully ticked, which made them read as one
  escalating control.
- **The bulk bar says which is which** — "N selected on this page" versus
  "N selected — everything matching this search".
- **The blast-radius cap went from 5,000 to 10,000.** Real mailboxes are that
  size and stopping halfway made people run the same cleanup twice. The wall
  still exists and the UI still says when a search exceeded it.
- **Ctrl+K hand-off no longer narrows.** The palette lists results from every
  folder of every account, then handed the text to an `in:inbox` view, which
  silently dropped most of them. That search now opens as "Search results"
  with no folder scope. Choosing a section in the sidebar leaves it.
- **The palette footer says its list is the top 25**, not the whole match.

Also fixed: the root `typecheck` script ran bare `tsc --build` against a
`tsconfig.json` that does not exist, so it had never done anything. It now
fans out across the workspaces, which is what CI was already doing.

86 Playwright tests, green headed.

### Searching from a folder was hiding the mailbox

Follow-up to the above, reported against the deployed app: a search for a word
plus "has attachment" returned nothing while the mail plainly existed. It had
been archived, and archived mail is not `in:inbox` — so the folder the user
happened to be standing in was quietly excluding most of their own mailbox
from their own search.

Browsing a folder is still the folder. But the moment any filter is applied
the folder scope drops and the search covers everything except spam, the way
Gmail's own search does. The header says which it is ("Search results —
searching all mail: inbox, sent, archived and trash") and offers a one-click
"Only search Inbox" to narrow back, with "Search everywhere" to widen again
without retyping. The Trash view keeps its scope, because there the bin is the
subject.

The empty state now says which reach came up empty, rather than a flat
"Nothing matched those filters."

89 Playwright tests, green headed.

### The rest of the results now load themselves

Reported: "filter sirf usi page par lagta hai" — the filter looked like it only
applied to the page on screen. It never did; the query goes to Gmail and covers
the whole mailbox. But the results came back 500 at a time behind a "Load 500
more" button, so a search that had matched 1,323 messages presented as a search
that had matched 500, and one that matched 12 old messages could present as
nothing at all.

The view now pages the rest in on its own, up to the 10,000 bulk cap, showing
"Loading the rest — 1,000 of 1,323" with a **Stop here** to interrupt and
**Keep loading** to resume. When it finishes it says "All N matches loaded",
so a list that ends reads as complete rather than truncated.

The total comes from `resolve-query`, which pages message ids 500 at a time and
costs nothing next to the metadata behind them — so the real number is on
screen long before the messages it counts are.

89 Playwright tests, green headed.

### Auto-loading was the wrong answer, and Gmail said so

The automatic paging added earlier the same day is reverted. It hit Gmail's
per-minute quota almost immediately and the API started refusing:

    403 PERMISSION_DENIED — Quota exceeded for quota metric 'Queries' and
    limit 'Queries per minute per user' (15,000)

The arithmetic was never going to work. Every message on a page costs a
metadata read, so one 500-message page across three mailboxes is already about
half the minute's allowance — and the loop was set to fetch up to ten thousand.

What ships instead:

- **Pagination stays manual.** The page shows 500 and a "Load 500 more"
  button. What was actually wrong was never the paging; it was that a page
  looked like the whole answer.
- **So the page now states the whole answer**: "Showing 500 of 1,323 matches",
  resolved from message ids, which page 500 at a time and cost almost nothing
  next to the metadata behind them.
- **Rate limits are retried, not shown.** Gmail signals a per-minute breach as
  a 429 *or* as a 403 whose body says `rateLimitExceeded` — the second reads
  like a permission failure and was being surfaced as one. Both now back off
  and retry up to four times.
- **Google's error envelope no longer reaches the screen.** A rate-limited
  search put six hundred characters of nested JSON in front of the user,
  project number included. It says one sentence now.
- **Appended pages are deduplicated.** A cursor that fails to advance replays
  its last page, and a list holding the same messages twice looks exactly like
  a filter that stopped being applied partway down. Nothing new in a page also
  ends the paging rather than offering another lap.

Also added: a **custom date range** (`after:` / `before:`) beside the age
presets. "Older than a year" cannot express "that job I had in 2019", and the
raw-syntax box is not an answer for someone who came here to avoid the syntax.
Gmail's `before:` is exclusive, so the end date is pushed out by a day to make
an inclusive-looking range inclusive.

92 Playwright tests, green headed.

### A custom calendar, real scrollbars, and pictures that show up

Three things that all came down to the same thing: the browser's own widget
does not know it is inside this app.

**Date picker.** `<input type="date">` styles its box and nothing else — the
calendar is drawn by the browser, so a pale panel dropped out of a dark app,
and a different pale panel on the next machine. `DatePicker.tsx` replaces it,
with the same bar the custom dropdown had to clear: arrows walk the grid a day
at a time, PageUp/PageDown change month, Home/End reach the ends of the week,
Enter commits, Escape closes, and the grid carries the roles a screen reader
expects. Month and year are dropdowns rather than chevrons, because reaching
2019 from 2026 by clicking eighty-four times is not a date picker. Values stay
`YYYY-MM-DD`, so nothing downstream knows it changed.

Dates are held at UTC midnight throughout. A calendar day is not an instant,
and `new Date(y, m, d)` read back as an ISO string lands on the day before in
any negative-offset timezone — which is how pickers end up off by one.

**Scrollbars.** There was no scrollbar styling at all, so every scrolling
surface drew the OS default: a grey trough with stepper arrows against a dark
rounded panel. Now themed, on `*` rather than `body` — the sidebar, the
message list and the reading pane each scroll in their own box, and a rule on
the page would have left all three untouched.

**Attachment images.** A photo showed as a filename and a broken-image icon.
Two causes behind one symptom:

- Attachments were only ever served `application/octet-stream` with a download
  disposition, so no `<img>` could ever render one. There is now an
  `?inline=1` mode — but the server decides, by **sniffing the magic bytes**,
  not by trusting a parameter or the sender's `Content-Type`. Raster formats
  only. SVG is an image and is deliberately excluded: it is a document that
  can carry script, and rendering one in this origin would run it with the
  session's cookies.
- A body that embeds its picture writes `src="cid:…"`, pointing at a
  `Content-ID` on an attachment part. The parser now keeps that id and the
  reader rewrites those references to the attachment endpoint, which is
  same-origin and allowed by the frame's CSP.

Remote `http(s)` images are still blocked and deliberately not rewritten:
loading one tells the sender the message was opened, and that is the tracking
pixel this app refuses to fire. There is a test asserting the request is never
made.

98 Playwright tests, green headed.

### Mailbox analysis

The empty half of the mail view now holds a dashboard: how much mail matches,
how much of it carries a file, who sent it, and a way to clear a sender out.

**The two halves are priced completely differently, and the UI says so.**
How many messages match and how many carry an attachment come from lists of
message ids — 500 an API call, so a hundred thousand of them is a couple of
hundred cheap calls and the numbers are *exact*. Working out who sent them
needs the `From` header of every single message, one metadata read each,
against a quota of about three thousand a minute. A hundred thousand messages
is therefore roughly half an hour of fetching for the sender list alone.

So the run reads the newest slice at a depth the user picks — 2,000 up to
Everything — reports exactly how deep it got, and says plainly when the list
is not the whole mailbox. The totals beside it always are. A sender list that
quietly described a fraction while looking like it described all of it would
be worse than no sender list.

Found while building it: reusing `MAX_BULK` for the id listing capped the
*counts* at ten thousand, so a hundred-thousand-message mailbox would have
reported a total of ten thousand — a wrong number presented as a fact.
`MAX_BULK` limits the blast radius of an action; nothing is destroyed by
counting, so the analysis uses its own, far higher ceiling.

Each sender row offers **View** and **Clear**:

- *View* fills the list beside the panel with that sender's mail. Clearing 812
  messages on the strength of a number alone is a leap — an address you
  half-recognise could be receipts — and the answer has to be reachable
  without losing an analysis that took minutes.
- *Clear* always **trashes**, never deletes. A chart is a place to notice
  something, not a place to destroy mail from; permanent deletion stays behind
  the typed confirmation in the Trash view, per ADR 0002. There is a test
  asserting `delete-forever` is never called from here.

A finished run is kept in `localStorage`, so a reload does not throw away
minutes of work and a slice of the quota. Only counts and sender addresses —
the same metadata already on screen, on the reader's own device, never a
message body. If the filters change after a restore, the numbers are marked as
belonging to the old ones and **Clear is withheld** until it is re-run: it
builds its query from the controls, so acting on stale figures would trash a
different set of mail than the number on screen. View stays enabled, because
looking is reading.

107 Playwright tests, green headed.
